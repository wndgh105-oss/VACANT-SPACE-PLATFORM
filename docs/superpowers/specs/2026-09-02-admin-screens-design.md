# 운영자(관리자) 화면 설계 스펙

- 작성일: 2026-09-02
- 관련 문서: [모두의창업_지원서_초안.md](../../../../모두의창업_지원서_초안.md), [2026-09-02-tenant-screens-design.md](2026-09-02-tenant-screens-design.md), [2026-09-02-landlord-screens-design.md](2026-09-02-landlord-screens-design.md)
- 범위: 단기 임대형 모듈 창업 플랫폼의 **운영자(관리자) 측 MVP 화면**만 다룬다. 창업자·건물주 측 화면은 앞선 두 스펙에서 이미 정의했다.

## 1. 배경 및 목표

창업자 스펙과 건물주 스펙 양쪽에서 "상태 변경은 운영자 전용"으로 남겨둔 기능(신청 상태 관리)과, 양쪽 화면이 전제하고 있던 "표준 장비 패키지" 데이터의 등록 주체(장비 패키지 마스터 관리)를 다룬다.

## 2. 범위 결정 사항

| 항목 | 결정 |
|---|---|
| MVP 핵심 기능 | 신청 상태 관리(대기중→연락중→확정→반려) + 장비 패키지 마스터 관리 |
| 장비 패키지 등록 방식 | 운영자 화면에서 직접 CRUD로 등록/수정 (DB 직접 입력이 아닌 화면 제공) |
| 확정↔공실 마감 연동 | 신청을 "확정"으로 바꾸면 해당 공실이 자동으로 "마감"으로 전환. 반대로 "확정"에서 다른 상태로 되돌리면 공실도 "공개중"으로 함께 되돌아감(양방향 연동) |
| 계정 체계 | 창업자·건물주와 분리된 관리자 전용 로그인 (가입 화면 없음, 계정은 사전 발급) |

## 3. 정보구조 (Sitemap)

채택 접근: **통합 리스트형**. 운영자는 특정 공실 단위가 아니라 "지금 처리해야 할 신청 전체"를 기준으로 일하므로, 모든 공실의 신청을 하나의 테이블에 모아 필터링·처리하는 구조를 기본으로 한다.

```
운영자 로그인
      │
      ▼
전체 신청 관리(홈) ──(행 클릭)──▶ 신청 상세(사이드 패널/모달) ──(상태 변경: 확정)──▶ 연결된 공실 자동 마감
      │
      ▼(별도 탭)
장비 패키지 마스터 관리 ──▶ 등록/수정 폼 (변경 즉시 창업자·건물주 화면에 반영)
```

## 4. 화면별 상세

### 4.1 운영자 로그인
- 이메일 + 비밀번호. 창업자·건물주와 분리된 관리자 계정 체계, 별도 가입 화면 없음(계정은 사전 발급)

### 4.2 전체 신청 관리 (홈)
- 테이블 컬럼: 신청자명, 연락처, 공실(주소 간략), 희망 계약기간, 희망 시작일, 신청일, 현재 상태
- 상단 필터: 상태, 공실 검색, 신청자 이름 검색
- 상태 컬럼은 인라인 드롭다운으로 즉시 변경 가능, 행 클릭 시 상세 패널도 함께 열림
- 기본 정렬: "대기중" 상태 우선 노출, 최신 신청순

### 4.3 신청 상세 (사이드 패널 또는 모달)
- 신청자 정보(이름/연락처), 요청 메시지, 희망 계약기간·시작일, 연결된 공실 정보(주소/임대료/업종) 요약
- 상태 변경 버튼: 대기중/연락중/확정/반려 간 자유롭게 전환 가능(제한 없음)
- "확정"으로 변경 시: "이 공실이 자동으로 마감 처리됩니다. 계속할까요?" 확인 다이얼로그
- "확정"에서 다른 상태로 되돌릴 시: 공실도 자동으로 "공개중"으로 되돌아감(§2 연동 규칙에 따름)

### 4.4 장비 패키지 마스터 관리
- 목록: 업종별 패키지 카드(패키지명, 포함 장비 목록, 월 렌탈료)
- 등록/수정 폼: 업종 선택(카페/소매·팝업/기타), 패키지명, 포함 장비 항목, 월 렌탈료
- 변경 사항은 창업자·건물주 화면의 "표준 패키지" 노출에 즉시 반영됨

## 5. 예외 / 엣지 케이스

- **같은 공실에 대기중 신청이 여러 건일 때 하나를 확정**: 나머지 신청은 자동 반려하지 않고 "공실 마감됨" 배지만 표시, 운영자가 개별적으로 정리
- **상태를 잘못 변경한 경우**: 모든 상태 전환은 제한 없이 자유롭게 되돌릴 수 있음. 단 확정↔공실 마감 연동은 항상 유지
- **필터 결과 0건**: "조건에 맞는 신청이 없어요" 안내
- **참조 중인 장비 패키지를 삭제하려 할 때**: "이 패키지는 N개 공실에서 사용 중입니다" 경고 후 삭제 여부 재확인(삭제 자체는 차단하지 않음)
- **로그인 실패**: 일반 인증 오류 메시지, 별도 복구 플로우는 범위 밖(운영진이 직접 계정 재발급)
- **동시 편집**: MVP는 동시성 잠금 없이 마지막 저장이 반영되는 단순 처리(초기 운영진 인원이 적다는 가정)

## 6. 이번 스펙에서 제외한 것 (다음 스펙 후보)

- 계약 연장/이동/철수 처리 화면 (2개월 계약 만료 시점의 창업자 선택지 처리)
- 결제/정산 관리 화면 (여전히 오프라인 처리)
- 운영자 권한 분리(역할별 권한 구분)
- 신청 처리 통계/리포트 대시보드
- 공실 강제 비공개/블랙리스트 처리
- 알림 시스템(신규 신청 시 운영자 이메일/푸시 알림)

## 7. 데이터 모델 관련 메모

세 개 스펙(창업자·건물주·운영자)이 공통으로 참조하는 핵심 엔티티는 다음과 같이 정리된다. 실제 스키마 설계는 구현 계획(writing-plans) 단계에서 확정한다.

- **공실(Listing)**: 창업자·건물주 스펙에서 조회/등록, 운영자 스펙에서 상태(공개중/마감)가 신청 확정에 의해 자동 갱신됨
- **신청(Application)**: 창업자가 생성, 건물주가 조회, 운영자가 상태를 변경
- **장비 패키지(EquipmentPackage)**: 운영자가 등록/수정하는 마스터 데이터, 창업자·건물주 화면에서는 참조만 함

## 8. 다음 단계

- 이 스펙 승인 후, 세 스펙(창업자/건물주/운영자)을 종합한 구현 계획은 writing-plans 절차로 별도 작성한다.
- §6에서 제외한 "계약 연장/이동/철수 처리"는 아이디어의 핵심 차별점(§ 모두의창업_지원서_초안.md의 "안되면 빠르게 빠질 수 있고 잘되면 연장") 중 하나이므로, MVP 이후 우선순위가 높은 다음 스펙 후보로 권장한다.
